# 聖地クエスト アーキテクチャ方針

## 現在の基本構成

- `lib/main.dart`
  - アプリ全体の状態管理
  - 画面切り替え
  - イベント初期化
  - GPS初期化・位置更新
  - スタンプ獲得の最終的なUI連携
- `lib/models/`
  - DB/APIデータを表すモデル
- `lib/widgets/`
  - 各画面の表示と画面固有の操作
- `lib/*_service.dart`
  - Supabaseやローカル保存など、状態管理から分離できる処理
- `supabase/migrations/`
  - DBスキーマ、RLS、RPCなどの変更履歴

## 今回の物理地点ベース獲得

スタンプ獲得の単位は「seichi（札）」ではなく「physical place（物理地点）」とする。

1. GPSがある物理地点への到着を検出する。
2. その地点に紐づく全seichiを対象にする。
3. 獲得時刻に有効なイベントだけを対象にする。
4. 同一地点の複数札を同時に獲得する。
5. 同時点で有効な複数イベントには、それぞれのイベントとして履歴を記録する。
6. 後から開始したイベントへ過去の訪問を遡及させない。

このイベント判定はDB側の `record_place_visit` RPCを正とし、クライアント側でイベント期間判定を重複実装しない。

## ローカル保存・オフライン

- 既存の `recordCollection` は互換性のため当面維持する。
- 新しい物理地点訪問は、既存キューと区別できる形式で保存する。
- オンライン復帰時に物理地点訪問をRPCへ送信する。
- 同じ訪問の再送が発生しても、DBの一意制約とRPCの冪等性によって二重獲得を防ぐ。

## コレクション画面

- 既存のスタンプ一覧を継続利用する。
- 札は1札ずつ表示する。
- 複数イベントで獲得した札は、実際に獲得したイベントを表示できるようにする。
- 「獲得一覧」のような別画面は追加しない。

## 今後の分割方針

大規模な一括リファクタリングは行わない。変更単位ごとに責務を分離する。

優先順位:

1. 物理地点ベース獲得サービス
2. コレクション状態・イベント履歴の読み込み
3. GPS/位置判定
4. イベント管理

`main.dart` は最終的にアプリ全体の状態と画面連携を中心にし、個別の業務ロジックをサービスへ移す。ただし、各分割後に `flutter analyze` と実機動作確認を行い、既存機能を壊していないことを確認してから次へ進む。

## 変更時の記録ルール

各変更では、以下を明確にする。

- 対象ファイル
- 変更理由
- 変更内容
- 既存機能への影響
- 検証方法

不要なアップグレード、無関係なリファクタリング、既存GPS判定の作り直しは行わない。
